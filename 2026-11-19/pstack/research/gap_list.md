## 4. 実践で見せる論点（3段ごと、優先度順）

各項目は、なぜ既存にないか、どの段で見せるか、録画や Before/After の指標、小さく一晩で終わる題材、優先度を書く。上位を先に置く。

### 入口（note、10分で完全理解）

ここで勝つ条件は、辞典の網羅ではなく、**1本の実件で宣伝の約束を本物にすること**。図は1枚、動画は約2分、という部屋の合意に合わせる。

#### 1. 寝る前に頼んで、朝に証拠つきのPRが届く（優先度: 最高）

- **なぜ既存にないか（事実）:** 競合本の宣伝と第9章の題がこの光景そのものだが、第9章は有料で 2,181字しかない。無料章にも、公式ガイドの [07-overnight.md](https://github.com/cursor/plugins/blob/main/pstack/docs/guide/07-overnight.md) にも、公開された一晩のPRと朝の監査ログはない。日本語の解説も手順の紹介に留まる。
- **見せる場面:** 就寝前の指示全文と時刻、朝のPR、`/show-me-your-work` または `/ketchup` の要約、判断ログの行。動画は「頼む → 証拠つきの『直しました』 → 朝のPR」の3点に絞る。
- **Before/Afterの指標:** 依頼時刻とPR作成時刻（時差）、完了条件を満たす検査の合否、人間が途中で手を入れた回数（0が理想、入ったら理由を書く）。
- **題材候補:** `sns-media-public` で、記事中の図URLが古いコミットを指したままになる問題を見つける小さな検査ツール。今日の制作でも実際に起きている。範囲が閉じ、合格条件（全リンクが 200 を返す／または古さの報告が出る）を一文で書ける。
- **事実と解釈:** 「一晩で検証済みPRが届く」は公式ガイドが勧める進め方（事実）。それが私たちの題材で何時間・何回の介入で届くかは、実行するまで分からない（未検証）。

#### 2. 「直しました」に証拠がつく／つかないの対比（優先度: 最高）

- **なぜ既存にないか（事実）:** 無料章は原則として「証拠がなければ完了ではない」と書くが、証拠なしの報告と、録画やコマンド出力つきの報告を並べた実件がない。
- **見せる場面:** 同じ依頼を、検証スキルなし（または `/poteto-mode` なし）で一度、検証スキルありで一度。入口の動画ではこの対比を短く見せ、詳細はTechブログへ。
- **Before/Afterの指標:** 報告に実物の証拠（コマンド出力、画面、不合格も残した検査）があるか。判定不能（inconclusive）と書いて止まれたか。
- **題材候補:** 上記ツールの「壊れたURLを1本仕込んだ状態」と「直した状態」。故意に壊した入力で、検査が落とせることも示す。

### 真ん中（カンリー Techブログ、1時間で再現できる実録）

入口の同じ実件を、再現手順・失敗・環境の差まで残す。競合本の第3〜4章と第11章が「説明」で終わる地点を、ログで越える。

#### 3. 本家をクラウドエージェントで回したとき、何が起きるか（優先度: 高）

- **なぜ既存にないか（事実）:** 公式READMEとガイドは、Custom Mode が [Agents Window と CLI](https://cursor.com/docs/cli/using) で使えること、`/in-cloud` や Projects のクラウドサブエージェントを書いており、prep.md 第2節に整理済み。一方、Cursor公式フォーラムでは、マーケットプレイスの `/poteto-mode` はクラウドエージェントの Custom Mode に乗らない、と職員が [2026-11-08](https://forum.cursor.com/t/cloud-agent-option-skill-does-not-enable-custom-mode-e-g-poteto-mode/177690) に回答している（回避策は、スキルをリポジトリの `.cursor/skills/poteto-mode/SKILL.md` に置くか、メッセージごとに `/poteto-mode` を付ける）。競合本の無料第4章は CLI とクラウドサブエージェントには触れるが、この制限には触れていない。2026-11-19 時点で「直った」という公式の追記は、当該スレッドには見当たらない。
- **見せる場面:** 同じ題材を、(a) Cursor のローカル Agents Window または `cursor-agent` CLI、(b) クラウドエージェント（プラグインのまま／リポジトリにスキルを置いた場合）、必要なら (c) Claude Code の公式導入、で並べる。クラウド側は画面録画の代わりに、エージェントの作業記録・PR・成果物を証拠にする（コーディングの使い手さんの方針どおり）。
- **Before/Afterの指標:** `/poteto-mode` がプレイブックをTODOに写したか、検証ステップが走ったか、回避策の有無。
- **題材候補:** 論点1と同じ検査ツールを、環境だけ変えて1回ずつ。一晩を超えない。
- **解釈にしないこと:** 「クラウドでは本家が使えない」と一般化しない。使える条件と、今の制限を実測して書く。

#### 4. 書いた本人ではないモデルが、検証で反対したか（優先度: 高）

- **なぜ既存にないか（事実）:** 無料第1章は「書いた人に採点させない」と書く。無料章にも既存の日本語解説にも、パネルが実際に差し戻したログは公開されていない。
- **見せる場面:** 実装エージェントの「完了」と、別モデルの検証（swarm / パネル）が残した不合格や条件付き合格。Techブログに原文を載せる。
- **Before/Afterの指標:** 差し戻し回数、最終的に残った差分の行数、検証側が指摘して直した項目数。
- **題材候補:** 論点1のPR。検証を「通った」だけでなく、一度は落とすケース（故意の欠けた検査）も残す。

#### 5. コスト、所要時間、人間の介入（優先度: 高）

- **なぜ既存にないか（事実）:** 無料第3章はコストの抑え方を一般論で書く。一晩の実件で、トークン・経過時間・介入回数を公開した日本語記事は見当たらない。
- **見せる場面:** 開始・終了時刻、モデル、概算トークンまたは請求、人が止めた／書き直した箇所の一覧。失敗とやり直しは消さない。
- **Before/Afterの指標:** 介入回数、やり直し回数、小タスクに `/poteto-mode` を使った場合の無駄（公式ガイドも「自明な修正には使うな」と書いており、それを実測で確認する）。
- **題材候補:** 本番の一晩（論点1）に加え、意図的に小さすぎる修正を1件やって「使わない判断」も残す。

#### 6. 公式の Claude Code と、Cursor 専用機能のスキップ（優先度: 中）

- **なぜ既存にないか（事実）:** 無料第3章は公式の入れ方を書く。第三者の移植版（`michael-denyer/pstack-claude` など）に頼る必要は、公式にはない（prep.md）。ただし [claude-code.md](https://github.com/cursor/plugins/blob/main/pstack/docs/harness/claude-code.md) がスキップすると決めたもの（Automations、Bugbot、クラウドエージェント本体）と、Issue #1270 のモデル名問題を、並走ログで示した記事はない。
- **見せる場面:** 同じ題材の「Skipped in Claude Code: …」行と、Cursor側でそのステップがどうなったか。
- **題材候補:** 論点3の比較枠に含める。移植版は「本家の代わり」ではなく、必要なときだけ対照用。

### 奥（10万字級の辞典。各項目に実行ログ）

競合本の第5〜7章（辞典、合計約3万字、有料）に対して、こちらは全項目を実際に動かし、動かしていないものは「未検証」と書く。文字数は解説の書き足しではなく、ログで埋める。

#### 7. 58スキル＋22プレイブックを、実行印つきで残す（優先度: 高。辞典の本体）

- **なぜ既存にないか（事実）:** 競合本は「1つ残らず解説」が売りで、第6章だけで 15,801字。実行結果の印や短い動画は、目次上は見当たらない。既存の辞典記事は版が古くなりやすい（例: [jnstさん](https://zenn.dev/jnst/articles/pstack-cursor-plugin) は 45スキル期の記述）。
- **見せる場面:** 各項目に「公式の一行（prep.mdを転用）／実際に動かしたか／所要／結果のログまたは短い画面／失敗」。入口の一枚図の番号と、辞典の見出しを一致させる（世界的イラストレーターさんの案）。
- **題材候補:** 本番の一晩で自然に発火した項目を厚くし、残りはコーディングの使い手さんが作る短い自動実行で「動く／動かない／対象外」を付ける。全部を一晩で人間が回す必要はない。
- **解釈:** 10万字は、全項目を長文解説すると届くが、それでは競合と同じ辞典になる。ログと失敗を残して初めて差になる。

#### 8. 形式検証と statechart を、小さな実件で使う（優先度: 中〜高）

- **なぜ既存にないか（事実）:** poteto氏が10月〜11月に繰り返し勧めている（上記の投稿）。無料第3章はスキル生成の提案に触れるだけ。公開された「自分たちの状態機械を図にして、仕様と突き合わせた」日本語の実件は薄い。
- **見せる場面:** 題材ツールの検査状態（未実行／失敗／成功）を `/create-formal-verification-skill` と `/statechart` でモデル化し、図と、見つけた（または見つからなかった）バグを残す。
- **題材候補:** URL検査の状態遷移だけに絞る。一晩の本作業のあと、短い追加で足りる。

#### 9. 敵対的レビューを減らし、検証にトークンを回したか（優先度: 中）

- **なぜ既存にないか（事実）:** poteto氏の [11月3日の投稿](https://x.com/poteto/status/2117437607940681849) と、karamageさんの [先行記事](https://zenn.dev/karamage/articles/5c3f8370b2b370) が同じ方向を語っている。競合本の無料章は原則の紹介に留まり、トークンの配分を実測していない。
- **見せる場面:** 同じ題材で、検証重視の走り方と、レビューパネルを厚くした走り方の、指摘の質とコスト。
- **注意:** 本の有料章がこの話をどこまで書いているかは未確認。差は「書いたかどうか」より「数字を出したかどうか」。

#### 10. 失敗をプロンプトではなく、検査や型に刻んだか（優先度: 中）

- **なぜ既存にないか（事実）:** 無料第1章の「教訓は構造に刻む」と、対談要約の中心メッセージ。一晩のあとに lint やテストや小さなCLIへ落とした記録は、公開実録としては見当たらない。
- **見せる場面:** 実行中に二度出た失敗を、翌日までに検査へ移し、同じ失敗が再発しないことを示す。`/correct` や `/automate-me` が使えたら、その出力も残す。
- **題材候補:** 図URL検査で見つかった失敗パターンを、リポジトリのチェックスクリプトにする。範囲が小さく、Before/Afterが分かりやすい。

## 5. 3段構成と、競合本がどちらも満たしていない点

萩野さんの「◯◯分で完全理解できる手軽さ」と「10万文字分の情報の膨大さ」は、部屋で決めた3段で両立する。調査から見た補強だけを書く。

1. **入口（note、約10分）:** 図1枚と2分の動画で、論点1と2だけを見せる。ここは 8,000〜10,000字でも、図と動画が先に全体を渡せば「10分」は保てる。競合本は「完全理解」を有料の第12章に置き、売り文句の一晩は有料の第9章（2,181字）に短くまとめていて、無料の入口だけでは約束の光景に届かない。
2. **真ん中（カンリー Techブログ、約1時間）:** 同じ実件の再現手順、失敗、環境差、コスト。競合本の無料第3〜4章は公式ガイドの日本語化に近く、ここにログがない。
3. **奥（辞典＋実行ログ、10万字級）:** 58＋22を、解説ではなく実行印で埋める。競合本の本体は第5〜7章の辞典（有料、合計約3万字）で、本全体でも 53,911字。網羅は有料で、実行証拠は見えない。こちらは無料で、未検証は未検証と書く。

入口の図の番号から奥の各項目へ、動画の各場面から真ん中の章へリンクする。手軽さと深さは別記事に分け、同じ実件でつなぐ。

競合本が満たしていない点（事実）: 無料で一晩の実件を見せない、本全体でも10万字に届かない、項目解説が主で実行ログが無料部分にない。公式の英語ガイド（[docs/guide](https://github.com/cursor/plugins/tree/main/pstack/docs/guide)）も、手順は詳しいが公開された実行ログではない。差は「より詳しい辞典」ではなく、「公開された証拠のある実録」になる。
