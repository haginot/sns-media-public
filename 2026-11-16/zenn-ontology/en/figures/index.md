# English figures for the Canly Tech Blog ontology article

English versions of fig1–fig7 from the Japanese article [一般的な「オントロジー」と、Foundry が「オントロジー」と呼ぶもの](https://zenn.dev/canly/articles/121db874319244). Wording follows [`../figures_text_en.md`](../figures_text_en.md). The cover banner is not in this folder; that English version is being made separately.

- Size and style are unchanged: 2000×1125 RGB PNG, same dark theme, isometric plates, and palette as the published Japanese figures.
- Sources used (latest of each): `v1/fig1.png`–`fig4.png`, and the fixed `figures_fix/fig5.png`–`fig7.png`.
- Rebuilt from the `figkit/zfig1.html`–`zfig7.html` sources, with Japanese labels replaced by the official English wording.

Changes from the Japanese originals, made so the figures match the English article (`e7f16a0`, HTML sources in [`src/`](src/)):

1. **fig4** has five steps, matching the caption. “Applied in a single transaction” is now part of ③ Rules instead of a separate step.
2. **fig6** follows the article's sequence diagram: `check_plan` comes before human approval, and the re-check happens inside `commit_rebooking`.
3. **fig7** no longer shows a number for Experiment II. It says only that the form made no difference, as the article does.
4. **fig5** no longer names the show. Step ① reads “public data from the show's official YouTube channel.”

| [fig1.png](fig1.png) | `v1/fig1.png` | Figure 1: The difference in scope between what general ontology and Foundry Ontology call "ontology" | Side-by-side comparison of what counts as “ontology.” Left: ontology in general (W3C standards), with a type layer (classes, properties, constraints; RDF, OWL, SHACL, SPARQL) and optional actual data (knowledge graph). Permissions and writes to business systems are outside the standards' scope. Right: Foundry Ontology (Palantir), where types, contents (objects and links), and components that make things happen (actions, functions, permissions) are all inside what Foundry calls “ontology.” A dotted line marks the two type layers as the same layer. | [fig2.png](fig2.png) | `v1/fig2.png` | Figure 2: The same range declaration works as inference in OWL / RDFS and as validation in SHACL | Inference and validation do different jobs. A small graph of ep001 and ep002 (episodes) and guest001, with `features rdfs:range Person` and `sh:class Person / sh:minCount 1`. Left panel, without inference: guest001 is not stated as a Person and fails the class check; ep002 has zero guests and fails minCount. Right panel, with RDFS inference: guest001 is inferred as a Person from range, so that violation goes away; the minCount failure remains. Footer: OWL doesn't treat unstated facts as false (open-world assumption); write required checks in SHACL. Illustrative example, run with pySHACL 0.40.2. |

This is close to “classes and properties” in ontology in general. The lower plate is the instance layer (objects and links): Theme: AI, Episode A, Episode B, Person X, Person Y. What is called a knowledge graph or object graph is mainly this layer. Episodes and people are fictional data. |
| [fig4.png](fig4.png) | `v1/fig4.png` (revised) | Figure 4: The flow of an action: parameters → submission criteria → rules → writeback and side effects → action log | An action defines how things get changed. Five steps: ① Parameters (input types); ② Submission criteria (who, and in what state; can be submitted only when all are met); ③ Rules (create, modify, delete objects and links / function rules; applied in a single transaction); ④ Writeback and side effects (writeback dataset, business systems / notifications, webhooks); ⑤ Action log (records successful submissions only). A rejection branch from step ②: not met → cannot submit (failures are tracked in action metrics). A permissions rail: roles / object and property policies (cell-level). The author’s view: this whole set of constraints is a “harness” (not a Palantir term). Example: change a flight's aircraft — only if the user is in the flight controllers group and the aircraft is in service. |
